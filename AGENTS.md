# AGENTS.md

Guidance for coding agents working in this repository. The specification is [docs/design.md](docs/design.md); read the section you are changing first.

## Commands (verified)

```sh
npm install          # dependencies (runtime: @modelcontextprotocol/server, @modelcontextprotocol/client, zod)
npm run check        # tsc --noEmit + all tests + privacy check; must pass before every commit
npm test             # node --test over test/**/*.test.ts (30 s per-test timeout)
npm run typecheck    # tsc --noEmit
node --test test/oauth-token.test.ts   # one file
node bin/t3-fleet-gateway.js --help    # CLI
node scripts/e2e-live.ts               # live check against a running gateway and real T3; never in tests (docs/operations.md)
npm run compat:check                   # manual developer check; read-only against T3, private local reports
node bin/t3-fleet-gateway.js webhooks list  # offline safe webhook counts; attempts <id> shows history, ping <id> sends synthetic content
npm run webhooks:smoke                 # isolated real-process HTTPS/retry/crash proof; Node 24+ and OpenSSL; no production access
npm run dashboard:demo                 # operator dashboard on a synthetic fleet (--scenario, --port, --no-badge, --webhook-receiver); never production data
npm run privacy:check                  # scan for private values ("Privacy and publishing"); -- --file <notes.md> for PR or release text, -- --commits <range> for commit messages
```

CI (`.github/workflows/check.yml`) runs `npm run check` on Node 24 and 26 (Linux) and 26 (macOS); `main` blocks force-pushes and deletion, and pull requests need CI green. `.github/workflows/privacy.yml` re-checks a pull request's title, description and commits whenever they change. No build step: Node 24+ runs `.ts` directly. There is no linter or formatter configured; match the surrounding style (2 spaces, single quotes, semicolons, ~140-column lines).

## Adding a tool

Define it with `defineTool` (see `src/mcp/fleetStatus.ts`): name, LLM-oriented description, `scope`, zod input and output schemas, and `run` returning `{ structured, summary }`. Add it to `gatewayTools` in `src/gateway.ts`. Throw `GatewayError` for failures; the registry turns it into an `isError` result with the code. Scope enforcement is automatic.

## Privacy and publishing

This repository is public and its history is permanent: removing something later takes a force-push. Keep the owner's private details out of code, tests, fixtures, docs, images (screenshots too), commit messages, PR or issue titles, bodies and comments, and release notes. The owner's name and email are fine. Never write:

- private repository names and their PR or issue numbers;
- real machine or host names and descriptions (hardware models of the owner's machines, nicknames);
- Tailscale tailnet names and any real `*.ts.net` hostname;
- local paths and user names (`/Users/<name>`, home directories);
- private or tailnet IPs (10/8, 172.16/12, 192.168/16, 100.64/10);
- webhook URLs, keys, tokens or any credential, even partial;
- real agent or bot wiring (which accounts or connectors are registered how, production scopes);
- production deployment specifics (versions installed on a date, counts of live jobs or watchers, retained backups);
- personal workflow notes and approval chatter ("X approved", "waiting on Y", rate limits), and family or employer details.

Use a placeholder instead:

| For | Write |
| --- | --- |
| hosts | `main`, `studio`, `host-a` |
| public URLs | `https://gateway.example.ts.net`, `<machine>.<tailnet>.ts.net` |
| repositories | `example-org/example-repo`; `example-org/WidgetWorks` where mixed case matters |
| paths | `/path/to/t3-fleet-gateway`, `~/.config/...` in generic form |
| users | `<user>` |
| IPs | RFC 5737 documentation addresses: `192.0.2.x`, `198.51.100.x`, `203.0.113.x` |
| agents | "a hosted agent (for example Grok Bot)" |
| evidence | "measured on a test machine" |

**Required self-check before every commit, PR, PR description edit and release:**

1. Run `npm run privacy:check`. Add `-- --file <notes.md>` for PR or release text you wrote to a file (`--stdin` works too) and `-- --commits origin/main..HEAD` for commit messages. It exits 1 and prints only `path:line` and a category, never the text; fix a finding by writing a placeholder. The summary line shows how many private denylist entries were loaded.
2. Re-read the diff and the text against the rules above. The check knows generic patterns and the owner's private list (the gitignored `.privacy-denylist`, or the `PRIVACY_DENYLIST` repository secret in CI; never print, quote or copy its entries); it cannot see an image, a nickname or a sentence about a deployment.
3. Do not paste a real value into a test or doc to show what the check catches: build synthetic ones at run time (`test/privacy-check.test.ts`). A rare intentional fixture carries `privacy-check: allow` on its line, or a justified entry in `scripts/privacy-allow.json`; neither can skip a private denylist entry.

CI runs the check on every pull request, title and description included, and again when the description is edited. An optional local hook runs it before each push: `git config core.hooksPath .githooks`.

## Invariants

- Never log tokens, approval or pairing codes, authorization headers, task text, worker messages, questions/options/answers, discovered catalog content (T3 project names, models, options, constraints) or command stdout/stderr/argv. Never return credentials or secret command data. Authorized tool output deliberately includes worker messages, actionable questions and catalogs; keep content out of logs and event details. `test/logging.test.ts` checks this; extend it when adding flows.
- Agent tokens and codes are stored only as hashes; T3 credentials only in `host_credentials`, and never leave the gateway.
- A new T3 credential is saved only after `t3_environment_read` succeeds with it.
- State-changing T3 calls must not be retried blindly: `T3Client.callTool` retries transport failures only with `readOnly: true`. A lost launch response is `unknown`, never relaunched. Use `T3TransportError.delivery` to tell `not_delivered` from `unknown`; resend a send only with the same T3 `clientRequestId`. Interrupt keys are per run (`cancelRequestId(jobId, runId)`): the same key re-delivers an interrupt for the same run, and a new run gets a new key.
- Job state changes go through `JobStore.transition` (guarded by the expected `from` states, event appended in the same transaction). Event details hold gateway-generated reasons and codes only.
- The engine is driven by `tick()` in tests (`jobEngine: { autoStart: false }`); tests move time with the injected clock, never with sleeps, except the agent-path test that runs the engine on a short timer.
- The fake T3 follows T3's published tool schemas (strict inputs). When T3's tools change, update `src/t3/schemas.ts` and the fake together; fixtures stay synthetic.
- `t3_thread_read` has two views over shared positions, and the fake models both: `messages` (T3's default) returns only user messages, assistant messages and proposed plans; `activity` returns every item (`subagent`, `notification`, reasoning, tools, commands, checkpoints, and the messages). Every read names its view (`T3Client.readThread` requires `view`) and states why in a comment or the design: replies, state, `read_position` and `work_messages` come from the messages view; delegated work from the activity view (`activity_position`). Put items a real T3 shows only in the activity view into tests through the fake's helpers (`addActivity`, `delegate`), so a read in the wrong view fails a test.
- Migrations are append-only from now on: a deployment runs on a database that has applied them, so never change what a migration on `main` produces; add a new one. (Making one more tolerant of the databases it starts from, without changing the schema it produces, is allowed: migration 2 copies whatever columns an older build of migration 1 left; see `rebuildJobsV2`.) A change ALTER TABLE cannot make (a CHECK constraint, say) rebuilds the table with `rebuildsTables: true` (see migration 2); a migration that must look at the database first uses `run` instead of `sql`. `migrate` reports any failure as `database_error` naming the migration. Test every migration on a database at the previous version that holds data (`test/storage.test.ts`). `job_events` is append-only (enforced by triggers).
- Error codes in `src/errors.ts` and OAuth error strings are a stable contract.
- The operator dashboard has read-only monitoring plus webhook connection management only, and is never on the MCP listener: no dashboard route on the MCP router and no MCP/OAuth route on the dashboard's (`test/dashboard.test.ts` checks both ways). Building its snapshot never calls T3 (only Run checks does, read-only, and never runs a command). It shows codes with fixed text, never error messages; never tokens, hashes, codes, credentials, command argv/output, task text, worker messages, questions, delegated task titles or catalogs; unknown times stay null. Every list is bounded. The page builds its DOM with `createElement`/`textContent`/`setAttribute` only and links only to `#/` routes and `t3-thread://v1/<safe id>`; no inline script or style (CSP). No login, cookie or browser storage: the network is the boundary, so anyone who can reach it can manage webhook destinations (docs/security.md). Webhook mutations need the custom API header, bounded JSON, mandatory exact request-host Origin (HTTPS except literal loopback) and same-origin fetch metadata when present. Never return saved URL/path/header material; clear pasted auth after submission or close. Config-owned rows cannot be replaced/disconnected by the UI; startup reconciliation only touches config-owned rows. Pings run outside transactions through the real sender transport; creation/replacement commits only after success and a fresh revision check. A failed replacement preserves the old route, disconnect cancels its queue, and late results must never resurrect it. Reject writes before readiness/after shutdown starts; abort and drain awaited pings before closing SQLite.
- Discovery is opt-in per host and authorization comes first: `fleet_projects`, `fleet_models` and `work_start` check the agent's grant on the host before the registry, the catalog cache or T3 is touched, and before any metadata or error about the host is produced (an unknown or unreadable host is a generic `not_found`). Catalogs are read on demand only (no timers), sanitized to a whitelist, bounded (beyond a bound the whole catalog is `catalog_limit`, never cut) and never logged. A T3 project that a configured alias maps to is always launched as that alias; targeting by id must never get around `allowWorkStart: false`, `runtimeMode` or any other alias setting. An explicit model selection is validated against the host's fresh catalog at creation and again right before the launch, and is never substituted. Alias-only `work_start` requests without a selection (worktree or scratch alias, and the host-only `target: { host }`) must keep their pre-discovery request-id hash (`startInputHash`) and stay downstream-free until dispatch: a scratch plan is built from the configuration, so such a job queues with the host down.
- Scratch (projectless) work is operator-pinned and fails closed. Only an alias with `workspaceMode: 'scratch'` and an explicit `t3ProjectId` pin launches scratch, and it sends `t3_thread_launch` `scratch: true` with no `projectId` and no `workspaceStrategy` (T3 refuses them together; T3 files the thread under its own scratch project, in a folder of its own); no tool input supplies a root, path, branch or strategy. The pin must be T3's NoProject/scratch project id: it is only validated against the host's projects before the launch and used for the project-scoped lookup of a lost launch response. If T3 returns another project id the job keeps following the thread and logs the fixed warning `job.scratch_project_mismatch` (job and host ids only). A scratch pin may not be shared with a non-scratch alias on the same host (config). `work_start { target: { host } }` authorizes the host first, then needs the host's `defaultProject` (a scratch alias on that host) and no discovery; an explicit `projectId` and a model selection still need discovery. A named project that cannot be resolved is `not_found`, never scratch. A scratch job is built from the configuration alone (no read of T3, no T3 project name recorded, so `projectName` is null; an explicit model selection is validated against the fresh catalog) and records a version 2 launch spec (host id, scratch workspace, the default binding when the host default chose the alias) with its alias policy and model; the dispatcher reads the host's projects and rechecks pin, host, workspace mode, runtime mode, ceiling and default binding right before the launch and fails the job without launching (`launch_policy_changed`, or `project_not_configured` / `project_not_found`). Its request-id hash covers the original host-only intention, so a changed default never moves a replay.
- A stored launch spec this build cannot read (damaged, or written by a build that knows more) is never read as no spec and never fails a read. No spec means an alias job, which dispatches as a worktree from the config, so `toJob` keeps `launchSpec: null` and sets `launchSpecUnreadable`; one bad row must not stop the dispatch, watch, tool or dashboard reads of the others (`JobStore.#job` reports it once per process, ids only, never the text). The dispatcher fails a queued job in that state through a guarded transition (`database_error`, the fixed message "This job's stored launch plan could not be read. Start the work again.") before any T3 call and never launches it; the jobs behind it still dispatch in that tick. A job with a thread is watched as usual, and views leave out what only the spec said (its workspace mode is null, unknown, not a worktree). Stored jobs are read through `JobStore.get(id, scope)`, which filters by host in SQL, so a job the caller may not see is indistinguishable from an unknown id. A repeated `work_start` request id is checked against the caller's operable hosts before the current alias is resolved (the alias may since have moved, been renamed or removed) and answers from the ledger without a downstream call; the same check runs again inside `JobStore.create`'s transaction.
- Workspace selection is opt-in per host (`hosts[].workspaceProbeCommand`). Without it nothing changes: no spec for alias-only jobs, version 1 specs, `startFromOrigin: false`, legacy hashes, no downstream call before dispatch, and an explicit `work_start` `workspace` is `invalid_argument`. With it, acceptance still reads nothing: a version 3 spec records only the intent (the policy's `baseRef`, never a hardcoded `main`), and the probe runs at dispatch; nothing the probe returns is stored beyond the resolved kind and a hash of host plus canonical folder, and no folder, argv or output is logged or shown. Version 1 and 2 specs never probe. A probe failure fails or defers only its job (`probe_retry_at`, three attempts, only for timeout or exit 255); `JobStore.queued` leaves deferred and root-blocked jobs out in SQL so they cannot fill the window; the engine looks at a bounded window, bounded rounds and eight probes per tick. A T3 host failure is still a host failure. The engine's shutdown signal kills a running probe.
- At most one gateway-managed job per host and identical canonical folder path holds a root reservation (`jobs.workspace_root_held_at`, partial unique index); nested paths are not related. `JobStore` owns it, updating it from state, delegated work and unresolved resume attempts; claims (`JobStore.dispatch`) and resumes (`JobStore.reserveRoot`, called by `work_continue`/`work_respond` on an idle job before anything is sent) are enforced; each resume attempt owns an opaque token in `jobs.workspace_resume_tokens`, a known success settles only its own deduplicated operation, while a definite failure removes only its own token (`abandonResume`) and frees the folder only when no token is left, an unknown outcome keeps its token, and every attempt restarts the grace period, T3-originated activity is only recorded (`workspace_root_contended`). Never hold it in memory only, never serialize worktree or scratch jobs, never make a root-blocked job occupy a slot or the dispatch window. The reservation cannot see work started in T3 itself or standing jobs; do not claim a global lock.
- Erasable TypeScript only; `.ts` import specifiers; `import type` for types.
- No machine-specific values or secrets in the repo; tests use synthetic data and loopback ports.
- Fakes that simulate a host going away reset a connection once its first request arrives, never on accept (`fakeT3.ts`, `frontDoor.ts`). Node 26.0's fetch (undici) sets the socket's type of service while writing the request from the socket's `connect` handler; if the reset is already there, macOS fails that with `setTypeOfService EINVAL`, thrown as an uncaught exception that fails whichever test is running (a few in every thousand resets on accept). Resetting after the request arrives gives clients the same `ECONNRESET` without the race. Production `serve` ignores that error (`src/processErrors.ts`); tests deliberately do not filter it, so a new reset-on-accept shows up.
- Tests never release a port and bind it again (test files run in parallel processes, and another one may take it in between): servers listen on port 0 and keep their socket; a gateway that restarts keeps its URL through `test/helpers/frontDoor.ts`.
