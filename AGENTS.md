# AGENTS.md

Guidance for coding agents working in this repository. The specification is [docs/design.md](docs/design.md); read the section you are changing first.

## Commands (verified)

```sh
npm install          # dependencies (runtime: @modelcontextprotocol/server, @modelcontextprotocol/client, zod)
npm run check        # tsc --noEmit + all tests; must pass before every commit
npm test             # node --test over test/**/*.test.ts (30 s per-test timeout)
npm run typecheck    # tsc --noEmit
node --test test/oauth-token.test.ts   # one file
node bin/t3-fleet-gateway.js --help    # CLI
node scripts/e2e-live.ts               # live check against a running gateway and real T3; never in tests (docs/operations.md)
```

No build step: Node 24+ runs `.ts` directly. There is no linter or formatter configured; match the surrounding style (2 spaces, single quotes, semicolons, ~140-column lines).

## Adding a tool

Define it with `defineTool` (see `src/mcp/fleetStatus.ts`): name, LLM-oriented description, `scope`, zod input and output schemas, and `run` returning `{ structured, summary }`. Add it to `gatewayTools` in `src/gateway.ts`. Throw `GatewayError` for failures; the registry turns it into an `isError` result with the code. Scope enforcement is automatic.

## Invariants

- Never log or return tokens, approval or pairing codes, authorization headers, task text or worker message content. `test/logging.test.ts` checks this; extend it when adding flows.
- Agent tokens and codes are stored only as hashes; T3 credentials only in `host_credentials`, and never leave the gateway.
- A new T3 credential is saved only after `t3_environment_read` succeeds with it.
- State-changing T3 calls must not be retried blindly: `T3Client.callTool` retries transport failures only with `readOnly: true`. A lost launch response is `unknown`, never relaunched. Use `T3TransportError.delivery` to tell `not_delivered` from `unknown`; resend a send only with the same T3 `clientRequestId`. Interrupt keys are per run (`cancelRequestId(jobId, runId)`): the same key re-delivers an interrupt for the same run, and a new run gets a new key.
- Job state changes go through `JobStore.transition` (guarded by the expected `from` states, event appended in the same transaction). Event details hold gateway-generated reasons and codes only.
- The engine is driven by `tick()` in tests (`jobEngine: { autoStart: false }`); tests move time with the injected clock, never with sleeps, except the agent-path test that runs the engine on a short timer.
- The fake T3 follows T3's published tool schemas (strict inputs). When T3's tools change, update `src/t3/schemas.ts` and the fake together; fixtures stay synthetic.
- `t3_thread_read` has two views over shared positions, and the fake models both: `messages` (T3's default) returns only user messages, assistant messages and proposed plans; `activity` returns every item (`subagent`, `notification`, reasoning, tools, commands, checkpoints, and the messages). Every read names its view (`T3Client.readThread` requires `view`) and states why in a comment or the design: replies, state, `read_position` and `work_messages` come from the messages view; delegated work from the activity view (`activity_position`). Put items a real T3 shows only in the activity view into tests through the fake's helpers (`addActivity`, `delegate`), so a read in the wrong view fails a test.
- Migrations are append-only from now on: a deployment runs on a database that has applied them, so never change what a migration on `main` produces; add a new one. (Making one more tolerant of the databases it starts from, without changing the schema it produces, is allowed: migration 2 copies whatever columns an older build of migration 1 left; see `rebuildJobsV2`.) A change ALTER TABLE cannot make (a CHECK constraint, say) rebuilds the table with `rebuildsTables: true` (see migration 2); a migration that must look at the database first uses `run` instead of `sql`. `migrate` reports any failure as `database_error` naming the migration. Test every migration on a database at the previous version that holds data (`test/storage.test.ts`). `job_events` is append-only (enforced by triggers).
- Error codes in `src/errors.ts` and OAuth error strings are a stable contract.
- Erasable TypeScript only; `.ts` import specifiers; `import type` for types.
- No machine-specific values or secrets in the repo; tests use synthetic data and loopback ports.
- Fakes that simulate a host going away reset a connection once its first request arrives, never on accept (`fakeT3.ts`, `frontDoor.ts`). Node 26.0's fetch (undici) sets the socket's type of service while writing the request from the socket's `connect` handler; if the reset is already there, macOS fails that with `setTypeOfService EINVAL`, thrown as an uncaught exception that fails whichever test is running (a few in every thousand resets on accept). Resetting after the request arrives gives clients the same `ECONNRESET` without the race. Production `serve` ignores that error (`src/processErrors.ts`); tests deliberately do not filter it, so a new reset-on-accept shows up.
- Tests never release a port and bind it again (test files run in parallel processes, and another one may take it in between): servers listen on port 0 and keep their socket; a gateway that restarts keeps its URL through `test/helpers/frontDoor.ts`.

## Status

Round A (OAuth, MCP endpoint, `fleet_status`, T3 client, enrollment, CLI), round B (the job layer: `work_*` tools, dispatcher, watcher, reconciliation, live end-to-end script), round C (review fixes), round D (review and live-run fixes: per-run interrupt keys, per-job error isolation, launch-error lookups, `stateChangedAt`, host `defaultModelSelection`) and round E (polish: `launch_not_started` for a found thread without a run, failed post-launch lookups stay `unknown`, unreadable search matches skipped, shutdown no longer waits for the startup model check, a gateway-specific `doctor` public URL check) are done. Round F added standing jobs (an existing T3 thread the operator adopts with `jobs adopt`; never launched, no slot, `work_cancel` interrupts only, `jobs release` ends it as `released`), `projects[].allowWorkStart` with `start_disabled` and standing jobs in `fleet_status`, schema migration 2, the launchd bootout wait and the CLI's EPIPE handling. The job layer's behavior in detail, including the T3 fields it relies on, is in docs/design.md under "Jobs → As built". A live run of `scripts/e2e-live.ts` against a real T3 confirmed launching into a fresh worktree and branch, a finished turn's shape and the exclusive `afterPosition` (a test in `test/jobs-derive.test.ts` uses that item sequence), follow-ups, and links; it also showed that T3 refuses launches without a model when the T3 project has no default. A later run through the public URL confirmed interrupting a running job (T3 thread `interrupted`, job `cancelled`) and that an `invalid_request` refusal leaves no thread. Questions, approvals and failed runs are not yet confirmed against a real T3; the script fails unless a cancel interrupts a running job (it retries once with a fresh job if the first one finished first). Round I (review fixes) followed a live look at a real coordinator thread: when it delegates, its own run completes while the child thread works; the child appears in the parent's timeline only as one `subagent` item (no creator; title = the child's task, text = its final summary once done); when the child finishes, T3 appends a `notification` item and starts a new parent run by itself. The gateway now follows `subagent` items that T3 shows as running (`waitingOnDelegatedWork`), reports turns the job starts by itself (`turn_started`, `turn_finished`), and only a worker message being written holds the read position. Round I also made migration 2 tolerant of early version 1 databases and wraps migration failures as `database_error`. Round I's detection read T3's default (`messages`) view, which never returns `subagent` items, so it could not trigger against a real T3; delegated work is now read from the activity view with its own position (`jobs.activity_position`, migration 4; see design.md, "Two views, two read positions"), and the fake models both views. Live, a `subagent` item is `running` (text: the child's task prompt) while its child works and `completed` (text: its summary) afterwards. Still unconfirmed live: adopting and driving a coordinator through the gateway end to end. After the final review: `waitingOnDelegatedWork` is the signal agents act on (it wins over the reply text); an idle job whose delegated work ends with no new turn gets a `delegated_work_ended` event and an attention entry; at most 200 delegated tasks are followed per job, with any beyond counted (`delegatedTasksUntracked`) and waited on until the coordinator has run a new turn; finished jobs keep no delegated work. After an agent missed the ends of replies cut at the 2,000-character excerpt: `work_messages` (read scope) reads a job's worker messages in full, live from T3 (up to 50,000 characters each, latest first by default, paged with `before`/`after`), `work_status` has `excerptTruncated` (migration 6), and `mine: true` includes standing jobs. Feed events stay code-only.
