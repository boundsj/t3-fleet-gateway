# Security

This document covers the threat model, what the gateway stores and where, and how it obtains access to T3 on your behalf. To report a vulnerability, see [SECURITY.md](../SECURITY.md).

## What the gateway protects

The gateway can make T3 Code start and steer coding agents on your machines. A stolen agent token with the `fleet:operate` scope is roughly equivalent to being able to type instructions into T3 at the gateway host's configured `access` level. The design keeps that power behind a human approval and narrow, revocable credentials.

## Trust boundaries

| Party | Trusted with |
| --- | --- |
| You (the operator) | Everything. You run the CLI on the gateway machine. |
| The gateway machine | The SQLite database, the HMAC key and T3 credentials. Anyone who can read the data directory as your user can act as the gateway. |
| Your tunnel | Transport only. It terminates TLS and forwards to `127.0.0.1`. It never sees anything but HTTPS requests and responses. |
| Agents (Grok Bot and other MCP clients) | Only what you approved: Read or Operate, on all machines (`fleet:read`, `fleet:operate`) or on selected machines only (`host:<id>:read`, `host:<id>:operate`). They never see T3 credentials. |
| T3 Code servers | Their own data. T3 never sees agent tokens. |
| Whoever can reach the dashboard (if enabled) | Reading operational metadata: host, client and job states, job titles, client names, granted access and success times, error codes; managing webhook destinations. No saved secrets, task text or worker content is returned. See "The operator dashboard". |

## Threats and mitigations

**Someone on the internet finds your public URL.** Registration is open (OAuth dynamic registration requires it), but registering grants nothing. Getting a token needs approval with a one-time code that only exists on the gateway machine. Codes are 50 bits of randomness, expire (15 minutes by default), work once, and failed attempts are throttled: 5 per authorization request, then that request is locked, and 20 per rolling hour across all requests, after which all approvals pause until the hour clears or you mint a new code. Registration itself is limited to 30 clients per hour; a client that has not completed an approval stops counting after 10 minutes, and clients that never complete one are deleted after a day. Throttle events are logged.

**Someone exhausts the throttles to lock you out.** Both global limits can be filled by anyone who can reach the public URL, so both are recoverable by you. `t3-fleet-gateway pair` starts a fresh approval-failure window whenever it mints a code (it says so when approvals were paused); 20 more guesses against a 50-bit code are negligible. Unapproved registrations stop counting after 10 minutes, so a burst of junk registrations blocks new ones for at most that long, and `t3-fleet-gateway throttle reset` clears both limits at once, including locked approval pages. `throttle status` shows how full they are. An attacker who keeps registering faster than the limit allows can still keep registration saturated; the gateway has no per-source limit, because the tunnel in front of it may not forward client addresses. If that happens, find the source in your tunnel's logs and block it there.

**A malicious page tricks you into approving.** The approval page shows the client name, the full origin it will redirect to, the requested access and, to choose from, the configured hosts' labels and ids; read them before approving. Anyone who registers a client can open an approval page, so host labels and ids are visible without an approval code: keep labels to names you do not mind showing. The form is bound to the exact request by an HMAC with a server key and expires after 10 minutes, so its hidden fields (redirect URI, PKCE challenge, state) cannot be swapped. Redirect URIs must match a registered one exactly and must be `https` (or `http` to a loopback host); the gateway never redirects to an unregistered URI. The one relaxation is RFC 8252 section 7.3: an `http` loopback URI matches with any port, because native clients listen on a port chosen at request time; scheme, host, path and query must still match exactly. The page loads no external resources, forbids framing, and has a strict Content Security Policy.

**The approval form never redirects.** Browsers apply a page's `form-action` to every redirect that follows a form submission, and block a disallowed one silently: an approval that answered with a redirect to the client's callback, whose own redirect led to another origin, left the operator on the approval page. So the form answers with a small page instead (same headers, no script) that navigates to the authorization response by meta refresh and shows a Continue link to it; denials and request errors go the same way. `form-action` stays `'self'`, and no directive in the policy restricts navigation. The page carries `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, so the authorization code in its URL is not sent as a Referer to the callback and is not cached. Submitting an approved form again (a double click, or Back and resubmit) shows the same response, as a link, while its code is unused and unexpired; the gateway keeps that URL, code included, in memory only until the code expires (60 seconds), and the fact of the approval until the form expires. A repeated form never gets a new code, spends no approval code and counts as no failed attempt. Only someone holding the signed form can repeat it, and the code is useless without the client's PKCE verifier.

**An authorization code is intercepted.** Codes live 60 seconds, need the PKCE verifier (S256 only), and work once. Replaying a used code revokes every token issued from it.

**A refresh token is stolen.** Refresh tokens rotate on every use. Presenting an already-rotated refresh token more than two minutes after its rotation, or after a token issued from it has itself been rotated, revokes the whole token family (all access and refresh tokens from that approval), which logs out both the thief and the client; the agent must be approved again. Within the two-minute grace window a rotated token gets another pair, so a client that lost a response, or sent two refreshes at once (MCP clients refresh without a lock), is never logged out: both pairs work. As soon as the client rotates one of those sibling pairs, the others are superseded, and presenting a superseded refresh token revokes the family. Unused refresh tokens expire after `refreshIdleTtlDays`.

*Residual risk: a superseded sibling's access token stays valid until it expires* (`accessTtlSeconds`, 12 hours by default). A thief who presents a stolen refresh token inside the grace window gets a sibling pair; its refresh token becomes useless once the client rotates (presenting it revokes the family), but its access token keeps working until it expires. The gateway does not revoke it when the sibling is superseded. That does not spare a legitimate holder of the pair: if two processes of one agent refresh at once and each keeps the pair it received, the process whose pair is superseded is logged out anyway once its access token expires, because its next refresh presents a superseded refresh token and revokes the family for both (accepting that refresh instead would give a thief the same way back in). Not revoking only delays that logout, and the delay is symmetric: a thief holding a superseded sibling gets the same window. The gateway keeps this behavior, so the benign race does not cut a working process off mid-task. If you prefer the stricter side, lower `accessTtlSeconds`, which shortens both the delay and the thief's window; to close the window at once, revoke the client with `clients revoke`. Agents should keep one token store per registered client, as MCP clients do: a process that keeps a superseded pair in memory and later refreshes with it revokes the family whether or not the access token was revoked.

**A bearer token minted with `clients token` leaks.** Such a token is a static secret kept by the agent's service (Notion, say) rather than an OAuth grant: it is not rotated, so whoever holds it can use it, with the access it was minted with, until it expires (one year by default, never with `--ttl never`) or you run `clients revoke`. Mint one only for agents that cannot sign in with OAuth, give it the least access the agent needs (`--access read` when it only follows work, `--hosts` when it needs only some machines), prefer a TTL you will notice, and revoke it if the service or account that stores it may be compromised. `clients list` shows each one with its expiry and last use. The gateway stores only its SHA-256 hash, never logs it, and binds it to this gateway's resource like any token; it belongs to a client with no redirect URI, so it can never be used to complete an OAuth authorization.

**The database leaks.** Agent access tokens (operator tokens included), refresh tokens and authorization codes are random 256-bit values stored only as SHA-256 hashes. Approval codes are stored as HMACs keyed with `gateway.key`, so a leaked database alone cannot be brute-forced offline for codes. T3 credentials are the exception (see below).

**DNS rebinding or a browser on the gateway machine.** Everything listens on loopback. `/mcp` rejects requests whose `Origin` header is present and not `publicUrl` (or listed in `allowedOrigins`); clients that send no `Origin` (server-to-server agents) are unaffected. Every `/mcp` request needs a bearer token, which a browser page cannot obtain. The gateway does not validate the `Host` header, because tunnels differ in what they forward and no endpoint grants anything based on network position alone.

**Oversized or malformed input.** Request bodies are bounded (16 KiB for OAuth endpoints, 1 MiB for `/mcp`), strings in registration are length-limited, and tool inputs are validated against schemas: tasks and follow-ups at most 20,000 characters, answers at most 16,000 characters of JSON, list and feed pages at most 100 and 200 items.

**An agent should reach only some machines.** Approve it for *Selected machines* (or mint its bearer token with `--hosts`). The gateway enforces the hosts on every tool, from the stored host of each job, before it calls T3 or returns anything from its ledger: `fleet_status` lists, counts and health-checks only those hosts, with their projects and standing jobs; `work_list`, `work_feed` events and attention are filtered in the database before their limits, so jobs elsewhere neither appear nor take a place on a page; `work_status`, `work_messages`, `work_continue`, `work_respond` and `work_cancel` answer a job on another host exactly as an unknown job id (`not_found`), and refuse a job on a host the agent may read but not operate with `insufficient_scope`. `work_start` checks the project's host and, for a repeated request id, the host of the job the id already started, so moving a project alias to another host in the config cannot hand back a job elsewhere; a repeated `work_continue` is checked before its stored result is returned. A restricted grant holds no fleet scope, so it never covers a host added later, and removing scopes only removes access: a refresh can keep or narrow a grant, never widen it (a client that asks for the generic fleet scopes on refresh keeps exactly its hosts; anything else beyond the grant is `invalid_scope`). Empty or malformed choices are refused, never taken for all machines; a refused form, including one with a wrong approval code, is shown again with the operator's choice rather than the request's defaults (configured hosts only, nothing the request's ceiling disables), so retrying it never widens the grant; and a stored scope the gateway does not recognize grants nothing. *Residual:* feed cursors are global event ids, so gaps between the ids a restricted agent sees show that other events happened, though never which job, host or content; and a grant naming a host id that is later removed regains access if a host with the same id is configured again.

**An agent learns more about a machine than you meant to show.** Discovery is off by default: agents see only the configured aliases. When you enable `discovery.enabled` on a host, agents with Read access to that host (and only that host) can list its T3 project ids and names and its provider instances, models and model options, read live from T3 and bounded in size; nothing else about a project (workspace paths, scripts, settings) is exposed. The host is authorized before the gateway reads or returns anything, so a host the agent may not read is reported exactly as one that does not exist. Browsing grants no launches: `work_start` into a project without an alias additionally needs `discovery.allowWorkStart` on the host and Operate on it, projects with an alias keep every rule of that alias (`allowWorkStart: false` included), and an explicit model selection is accepted only when the host advertises exactly it. Catalog content is never logged.

**An Operate agent misbehaves.** It can start and steer work only in the configured projects, each job in its own worktree and branch, at the project's `runtimeMode` (capped by the host's `access`), and at most `maxConcurrentJobs` per host at once; more jobs wait in the queue, which you can see with `work_list` or in `fleet_status`. A scratch alias is the exception to the worktree: its jobs run in a folder of their own in T3's internal scratch workspace (`workspaceMode: "scratch"`, used by `hosts[].defaultProject`; the launch sends `scratch: true`), with no worktree or branch from the gateway, so give that alias the `runtimeMode` you would give a machine's scratch folder, and pin only T3's internal scratch project (the gateway only checks that the pinned project exists, not what it is). Agents never supply a path, branch or workspace strategy. Every job is an ordinary T3 thread you can read and stop. Revoke the client to cut it off.

## Known limitations

- **No CORS on registration and token endpoints.** `/oauth/register` and `/oauth/token` send no CORS headers, so an MCP client running as a web page in a browser cannot complete sign-in. Server-side agents (Grok Bot and other hosted or native clients) are unaffected; the metadata documents do allow any origin.
- **No per-source rate limits.** The OAuth throttles are global (see above), because the tunnel in front of the gateway may not forward client addresses.

## The operator dashboard

The optional dashboard (`dashboard.enabled`, off by default) shows monitoring data and manages webhook connections. It has **no login of its own: the network is its boundary.** Whoever can reach it can add, replace, test and disconnect webhook destinations, including sending synthetic test requests from the gateway machine. It listens on loopback on a port of its own and is meant to be published with a tailnet-only proxy (`tailscale serve` on a path), so whoever can reach it is a process on the gateway machine or a device your tailnet admits to that machine. If you share your tailnet, restrict that path with your tailnet's access rules. On a machine with other local users, any local user can reach a loopback port: leave the dashboard off there, or accept that they can read what it shows and manage webhook destinations.

What it shows and never shows. It shows host labels, ids, T3 URLs and your transport notes, credential states and expiries, access ceilings and project policies; client names (including names unauthenticated registrants chose, shown as text), redirect origins, granted access, grant states and expiries, and success times; job ids, titles (the agent's title or the task's first line, as T3 shows the thread), projects, hosts, states, counts and T3 thread links; job event codes; check results. It never shows tokens, token or code hashes, approval codes, T3 credentials, the server key, the mint command or its argv or output, task text, replies, questions, options, answers, delegated task titles, catalogs, or error messages (codes only, with fixed text). Saved webhook URLs, paths, headers and authentication values are also never returned. Pasted authentication is cleared after submission or closing the form; no browser storage is used and no cookie is set. Tests check this (`test/dashboard.test.ts`).

How it keeps other origins out. A website you visit cannot read it through DNS rebinding: requests with a `Host` other than the listener's loopback address and port or an exact `dashboard.allowedHosts` entry get `421`. Its API needs a custom request header, which a cross-origin page cannot send without a CORS preflight the dashboard never grants, and refuses cross-site fetch metadata and foreign `Origin`s; all POSTs need JSON. Webhook management also requires a mandatory Origin with the exact request Host (HTTPS, except literal loopback), refuses `same-site` as well as `cross-site` fetch metadata, and bounds its request body to 16 KiB. The request session and UUID prevent replay within a bounded session; they are not a login or a substitute for the network boundary. Responses carry a strict CSP (`script-src 'self'`, no inline script or style, `frame-ancestors 'none'`), `X-Frame-Options: DENY` and `Cross-Origin-Resource-Policy: same-origin`. The page builds its DOM without parsing HTML and links only to its own views and `t3-thread://v1/<id>`, so stored text cannot become markup or a `javascript:` link.

Not on the public URL. The MCP listener, which your public tunnel carries, has no dashboard routes, and the dashboard listener has no MCP or OAuth routes. If a public tunnel were pointed at the dashboard's port by mistake, `doctor` and the dashboard's Run checks report it (they ask the public URL for the dashboard's API), and requests Tailscale marks as Funnel traffic (`Tailscale-Funnel-Request`) are refused; the Funnel marker is defense in depth that depends on Tailscale setting it, while the separate port is the primary control.

Run checks only reads: one `t3_environment_read` per host, the public URL's metadata, the database's quick check, file permissions and the mint executable's resolution. It runs no command, enrolls nothing and renews nothing.

## What is stored, and where

All state is in the data directory (default `~/.local/share/t3-fleet-gateway/`, mode `0700`; files `0600`). The gateway refuses to start if permissions are looser.

| Data | Where | Form |
| --- | --- | --- |
| Registered agent clients (name, redirect URIs, timestamps) | `gateway.db` | plain |
| Approval codes | `gateway.db` | HMAC-SHA256, single use |
| Client authentication success times | `gateway.db` | nullable timestamps, MCP sampled once per minute; old mixed usage is not backfilled |
| Authorization codes, access tokens, refresh tokens | `gateway.db` | SHA-256 hashes |
| Webhook destinations, authentication values, ownership and revisions | `gateway.db` `webhook_subscriptions` | **plain secrets**, never returned by the dashboard or CLI; protect database backups |
| Webhook pending payloads and attempt metadata | `gateway.db` `webhook_deliveries`, `webhook_attempts` | payloads cleared after completion/cancellation/expiry; safe attempt codes and times retained under bounds |
| T3 credentials, one per host | `gateway.db` `host_credentials` | **plain bearer tokens** (the gateway must present them) |
| HMAC key | `gateway.key` | 32 random bytes |
| Jobs: task text, thread titles and app links, the latest worker message excerpt (at most 2,000 characters), pending question ids | `gateway.db` `jobs` | plain, never logged |
| Launch spec of a job started with a target or a model selection: T3 project id and name, policy origin, base ref, runtime mode, the exact model selection | `gateway.db` `jobs.launch_spec` | plain JSON, never logged |
| T3 project and model catalogs for discovery | not stored: read from T3 when an agent asks, kept in memory for 30 seconds, returned to agents with Read access on that host, never logged | — |
| Full worker messages (`work_messages`) | not stored: read from T3 when an agent asks, returned to agents with Read access, never logged | — |
| Job events (state changes with gateway-generated reasons and codes; no content) | `gateway.db` `job_events` | plain, append-only |
| Request ids of `work_start` and `work_continue` with an input hash | `gateway.db` `idempotency_keys` | SHA-256 of the input |

Back up the data directory as a secret. Anyone who can read it can call T3 with the stored credentials until they expire or you revoke them in T3.

`clients diagnose` exposes only client/family ids, states, expiry ranges, revocation reasons and observed success timestamps; no credentials, tokens, hashes, task or message content. It reads stored capability without consuming/revoking tokens or starting downstream probes. A usable family does not prove the connector saved a valid sibling, and an offline store cannot prove reachability. Connectivity failures alone are not a reason to erase credentials or reauthorize; see [recovery](operations.md#authentication-and-outage-recovery).

## Logs

Logs are JSON lines on standard output. They contain event names, ids (client ids, token family ids, host ids, job ids), states, tool names, HTTP methods, paths without query strings, status codes and durations. They never contain tokens, approval or pairing codes, authorization headers, task text, worker message content, or discovered catalog content (T3 project names, models, options). The logger also replaces values under secret-bearing keys (`token`, `code`, `authorization`, `credential`, `task`, `message` and similar) as a backstop, and automated tests drive a full OAuth flow, MCP calls and an enrollment, and every job tool with distinctive task, follow-up, question, answer and worker text, and assert that none of it appears in the captured logs.

## The automated T3 consent step

T3 Code normally approves a new MCP client in a browser: you see the client and choose an access level. T3 also supports approving with a one-time **pairing code** minted by its CLI. The gateway uses that path so it never needs a browser:

1. It registers an OAuth client with T3 named `t3-fleet-gateway (<host id>)`, with a loopback redirect URI that is never followed.
2. It runs the host's `mintPairingCode` command (by default `t3 auth pairing create --ttl 5m --json`), reads the code from its output and never logs it.
3. It submits the approval decision to T3 with that code and the configured `access` level, then exchanges the resulting authorization code (with PKCE) for a T3 access token.
4. It verifies the new credential by calling `t3_environment_read`, and only then stores it.

This automates T3's consent step using **your own access to the machine**: the same access needed to run `t3 auth pairing create`. It grants nothing you could not grant yourself, but it does mean the gateway can renew its own access every month without asking. Keep that in mind when choosing `access`:

- `read-only` lets the gateway read T3 state only (enough for `fleet_status`).
- `approval-required` through `full-access` let it start threads, with T3 capping their runtime mode at that level. The gateway adds its own scopes and per-project `runtimeMode` on top.

T3 issues no refresh tokens; credentials last 30 days. The renewal loop re-enrolls a host when fewer than `renewWhenDaysLeft` days remain and keeps the old credential until the new one is verified. Old T3 sessions expire on their own; you can revoke them earlier in T3 under Settings → Connections, or with `t3 auth session list` and `t3 auth session revoke <id>`.

## Temporary outbound TLS key block

`src/tlsTrust.ts` blocks the eight compromised eMudhra/emSign intermediate **public keys** (CVE-2026-111943), using SHA-256 of DER SubjectPublicKeyInfo, including cross-signed/reissued certificates with the same keys. It does not remove any root or change any CA store. Unrelated Comodo/Sectigo chains through AAA Certificate Services remain usable, as do system CAs, `NODE_EXTRA_CA_CERTS`, and per-connection private CAs.

[Mozilla bug 2083449](https://bugzilla.mozilla.org/show_bug.cgi?id=2083449) and [Mozilla's announcement](https://blog.mozilla.org/security/2026/10/20/protecting-firefox-users-following-the-compromise-of-emudhra-intermediate-certificates/) confirm compromised intermediate keys, not compromised root keys. The hashes match [Node's native fix at d9a3f3d](https://github.com/nodejs/node/commit/d9a3f3d150f7959f2d448d9a61aa11f5a75aa2b3), Go's CVE-2026-111943 fix and [Electron #55126](https://github.com/electron/electron/pull/55126). The public fixtures in `test/fixtures/compromised-intermediates.json` come from the [disclosure inventory](https://emudhra.we-have-a-problem.com/impacted-intermediates.json); offline tests derive all eight SPKI hashes from all sixteen certificates (original and cross-signed) and prove they are blocked at different chain depths. Root fixtures prove that trust anchors are preserved.

The launcher installs the shim before dynamically importing the CLI; outbound modules also import it for direct use. For another entrypoint, preload it before application/tracing code:

```sh
node --import ./src/tlsTrust.ts app.js
```

The shim wraps `tls.connect()` and adds the key block to each connection's existing `checkServerIdentity`. This covers HTTPS, built-in fetch/undici and direct TLS connections, including custom hostname checkers; the caller's checker still runs for unblocked keys, and normal chain validation remains enabled. ESM named exports are synchronized. The approach was reviewed against the dependency-free [atproto preload](https://github.com/bluesky-social/atproto/blob/fc60876949cca1ca28e98273ecfc97a151d3ebfc/packages/internal/fetch-node/src/emudhra-preload.mjs); no package dependency is needed. Blocked keys fail with `CERT_REVOKED`; an unreadable certificate fails closed with `ERR_TLS_CERT_CHAIN_CHECK`. Neither error includes hostname, certificate or credential material.

Limits: resumed TLS sessions skip `checkServerIdentity`, so restart processes and discard sessions saved before installation; installing this after a connection has been established cannot protect that connection or its cached sessions. A custom hostname checker would bypass a plain global-checker replacement; composing at `tls.connect()` avoids that bypass here. `rejectUnauthorized: false` or `NODE_TLS_REJECT_UNAUTHORIZED=0` still permits unauthenticated connections and must not be used. Direct `TLSSocket` construction, alternative TLS libraries, references captured before the shim runs, incoming client certificates, and child processes/worker threads that do not load the shim are outside its coverage. An earlier `--require` preload can capture/open TLS before an `--import` preload runs. The JS check walks Node's exposed issuer chain; it cannot reproduce the native fix's full OpenSSL verification hook and may reject a peer-supplied path containing a blocked key even when another path is possible.

T3 HTTPS/MCP and its OAuth enrollment/token calls, webhook deliveries/setup tests, and public-URL/dashboard exposure checks use these TLS transports. There is no separate outbound identity-provider or GitHub API client in the gateway; GitHub PR links are metadata. HTTP/loopback traffic and child executables are unaffected. Root removal was rejected because it over-blocks legitimate sibling chains; AAA is not in Node's bundled store, though a system or extra store can trust it. No exemptions or CA-store changes are necessary for this key-based workaround.

Remove the shim once the minimum supported Node release includes [nodejs/node#66871](https://github.com/nodejs/node/pull/66871) and verification succeeds without it. That native fix enforces the same eight keys deeper in TLS verification. A merged PR alone does not identify a released version; confirm the release notes before upgrading the minimum.

After an operator deploys and restarts, run these from the checkout with the same Node runtime, CA environment and flags as the gateway:

```sh
TLS_LIVE_TEST=1 nice -n 10 node --test test/tls-trust-live.test.ts
TLS_LIVE_TEST=1 nice -n 10 node --use-system-ca --test test/tls-trust-live.test.ts
```

Each of `dv-g3b`, `dv-g3b-aaa`, `ev-g3c`, and `ev-g3c-aaa`, followed by `-emudhra.we-have-a-problem.com`, must fail with a certificate-validation error through fetch, HTTPS and TLS (including a custom hostname checker), on first and repeated attempts. DNS failures and timeouts do not count. Normal public TLS at GitHub and nodejs.org must still connect. These tests are skipped unless enabled and contact only public test sites, with no credentials. To exercise the key block even when a runtime already lacks an affected root, a private test process may additionally trust the public roots in `test/fixtures/tls-roots.json` through a temporary PEM bundle and `NODE_EXTRA_CA_CERTS`; set `TLS_REQUIRE_KEY_BLOCK=1` to require `CERT_REVOKED` specifically. It must still reject the compromised chains.

Separately verify the running gateway's read-only host health and public metadata, OAuth when next needed, and intended webhook deliveries (a synthetic webhook test sends content). Check code-only TLS diagnostics. Standalone tests prove policy in a new process, not that the running service was restarted with it. Do not publish configured destinations or private verification details in this repository.

## Revocation

- One agent: `t3-fleet-gateway clients revoke <client id>` revokes the client and every token issued to it, immediately, without a restart.
- The gateway's access to a T3 host: revoke its session in T3 (Settings → Connections, or `t3 auth session revoke`), and remove the host from the config or stop the gateway, since renewal would otherwise enroll again.
- Everything: stop the gateway and delete the data directory, then revoke its T3 sessions.

## Outbound webhooks

Subscriptions are trusted operator choices made through the private dashboard or configuration files, never destinations chosen through MCP agent tools. Dashboard access permits managing them; keep access limited to trusted operators. HTTPS with normal certificate validation is required by default. The explicit development HTTP exception accepts literal loopback only. Embedded URL credentials/fragments and transport/control auth headers are refused; redirects are never followed, so an auth header cannot be forwarded to a redirect target. Destination DNS and network access remain the operator's trust boundary: choose a receiver you control or trust and apply egress policy on the gateway host if needed. There is no inbound webhook receiver or public management endpoint; management routes exist only on the private dashboard listener.

For config-owned subscriptions, auth values come from private, owned, regular files in the data directory; empty, unreadable, oversized, symlinked or invalid-header values prevent an enabled route from starting. Files are opened without following symlinks and without blocking, so a FIFO is rejected before reading. For dashboard-owned subscriptions, the operator pastes the full header once; the gateway tests it and stores the route in the existing private database without writing a new secret file or changing global configuration. Route URLs and auth are private database material and never included in logs, API responses or diagnostic output. The two ownership types are separate: startup reconciles only config-owned rows and the dashboard cannot replace or disconnect them. Treat config and backups as secrets. Attempt logs contain fixed outcomes/status/timestamps/IDs only, no raw errors or responses. Response bodies are discarded under size and time limits.

Notifications contain job metadata including title; titles can be derived from task text, so choose a non-sensitive title. Worker excerpts are absent by default and should stay off when replies may contain secrets. A deliberate per-subscription opt-in sends at most 500 characters of worker text; arbitrary secrets cannot be reliably recognized or redacted. No task body, questions or transcripts are added. Reading details still requires the receiver's separate gateway MCP credentials and grant. A failed setup or replacement test never destroys a working route. A successful replacement checks the expected revision again after the network request, so a concurrent disconnect or newer replacement cannot be overwritten. Shutdown rejects new management work and aborts/drains pending tests before closing the database. Disabling/revising a route cancels old queued payloads and clears them; an already transmitted request cannot be recalled. Completed and expired payloads are cleared too. The normal private SQLite files, including WAL/backups, can retain old pages: clearing a payload is logical retention, not secure erasure.
