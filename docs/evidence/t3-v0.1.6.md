# T3 v0.1.6 source compatibility review

Checked 2026-10-31 against the public stable tags: v0.1.5 (`6d450a4284852af137b2f3407fddd89eb76e7644`) to v0.1.6 (`2359643cffa6ba9ee84d6f2694b935de54a8013e`). This is a source/contract check and synthetic-host verification, not a live v0.1.6 qualification.

## Calls the gateway makes

No removed input or incompatible output was found for thread read (both messages and activity), launch, send, settle, interrupt, model options, environment read or downstream authentication. There is one intentional launch behavior change: a provider can now reject a runtime mode it does not support.

- **Read:** the [MCP service diff](https://github.com/pingdotgg/t3code/compare/v0.1.5...v0.1.6) optimizes caller/task reads without changing the consumed thread/item/run response fields. Extra fields remain tolerated by the gateway's loose response schemas. Gateway state/replies still use the messages view; delegated work uses activity.
- **Launch:** [project handlers](https://github.com/pingdotgg/t3code/blob/v0.1.6/apps/server/src/mcp/toolkits/project/handlers.ts) preserve worktree/root/scratch inputs, explicit model selection and retry keys. The new provider-mode check uses [resolveRuntimeMode](https://github.com/pingdotgg/t3code/blob/v0.1.6/apps/server/src/mcp/delegatedTaskModes.ts): an omitted/inherited mode steps down to the broadest supported mode within the ceiling; an explicit unsupported mode returns `invalid_request` before launch. The gateway always supplies its recorded runtime mode and must not omit it to obtain a fallback. Such rejection already takes the definite-failure path, without relaunch or silent policy substitution. Upstream's [handler test](https://github.com/pingdotgg/t3code/blob/v0.1.6/apps/server/src/mcp/toolkits/project/handlers.test.ts) covers a provider lacking `auto`, inherited fallback to `auto-accept-edits`, and explicit rejection. Providers accepting the configured mode are unaffected.
- **Settle:** [ThreadOrganizeTool](https://github.com/pingdotgg/t3code/blob/v0.1.6/apps/server/src/mcp/toolkits/thread/tools.ts) adds `Tool.Strict`; it still accepts optional `threadId` and action `settle`. The gateway sends exactly `{ threadId, action: 'settle' }`, with no unknown fields. Its existing fake uses a strict input too. The compatibility probe now checks this sample locally when organize is advertised; it never settles a real thread.
- **Send/interrupt/model options:** the [orchestrator MCP contracts](https://github.com/pingdotgg/t3code/blob/v0.1.6/packages/contracts/src/orchestratorMcp.ts) and model selection wire forms used here are unchanged between these tags. Send's message/mode/request key, interrupt's thread/request key and optional reason, and explicit model option maps remain accepted. Model search changes matching semantics, not its shape; the gateway uses the returned catalog and does not guess selections.
- **Environment/auth:** optional `sideChats` and `projectOrganization` capability flags are additive in [environment contracts](https://github.com/pingdotgg/t3code/blob/v0.1.6/packages/contracts/src/environment.ts). The gateway only requires environment id, version and platform. [Auth contracts](https://github.com/pingdotgg/t3code/blob/v0.1.6/packages/contracts/src/auth.ts) wrap state, authorization code and PKCE verifier in `RedactedFromValue`; [McpOAuth](https://github.com/pingdotgg/t3code/blob/v0.1.6/apps/server/src/auth/McpOAuth.ts) unwraps them internally. Their HTTP string representations and authorization-code-only grant remain unchanged. The gateway's pairing/verified bearer flow is unchanged; provider-settings secret references are unrelated to MCP credentials.
- **Delete:** `thread.delete.onlyIfUnused` is optional. The gateway never deletes threads, so no code was added for it.

## Project organization

[T3 project responses](https://github.com/pingdotgg/t3code/blob/v0.1.6/packages/contracts/src/project.ts) add optional nullable `pinnedAt` and `archivedAt`; `pinned`/`archived` are mutation inputs, not the response fields. [ProjectService.listPage](https://github.com/pingdotgg/t3code/blob/v0.1.6/apps/server/src/project/ProjectService.ts) excludes deleted projects but retains archived ones.

`fleet_projects` now exposes nullable boolean `pinned` and `archived`: true for a timestamp, false for an explicit null, unknown/null when absent on older hosts. Archived projects remain visible with a warning in guidance. This preserves alias mapping and operator policy: removing archived rows could conceal a configured alias and let a different project with the same name resolve under a less restrictive discovery policy. These flags describe organization, not authorization; launch permissions remain operator-controlled. Pin/archive timestamps and other project settings are not exposed.

## Side chats

[Lineage](https://github.com/pingdotgg/t3code/blob/v0.1.6/packages/contracts/src/orchestrationV2.ts) adds optional `sideChat`, while [ThreadManagementService.listProjectThreads](https://github.com/pingdotgg/t3code/blob/v0.1.6/apps/server/src/orchestration-v2/ThreadManagementService.ts) and [ThreadSearch](https://github.com/pingdotgg/t3code/blob/v0.1.6/apps/server/src/orchestration-v2/ThreadSearch.ts) exclude side chats, including when subagents are requested. Thus `fleet_threads` already excludes them on v0.1.6. Crucially, MCP summary/detail does **not** expose `sideChat`: direct `t3_thread_read` reports the ordinary `fork` relationship.

Client adoption and adopted-job resume now verify that a fork appears in a fresh bounded project thread list. This closes direct-id adoption without inventing a wire flag or rejecting ordinary forks on older hosts. Missing/incomplete/oversized lists fail closed. Non-fork adoption keeps its existing reads. Operator standing-job adoption remains an explicit choice. The watcher follows ledger ids only and never imports discovered threads, so hidden side chats do not become normal jobs. A previously explicitly tracked thread remains followed; no destructive ledger rewrite is needed.

## Verification and limits

- `npm run check` checks types, all tests and privacy. Regression cases in `test/threads.test.ts` cover project organization (including absent legacy fields), hidden side-chat direct-id refusal, ordinary fork adoption and watcher isolation, and fresh resume refusal. Existing strict settlement, discovery/model selection, authentication and launch tests retain coverage.
- Manual CLI probe: `node scripts/check-t3-compatibility.ts --config <synthetic-config> --data-dir <temporary-ledger> --state-dir <temporary-state> --accept --json` returned exit 0 / PASS against an isolated loopback fake host, with 21 passing checks, both thread views and a seeded pending question, no skipped reads and no mutation calls during the probe. The fake advertised version 0.1.6; that is synthetic metadata, not an upstream server run. All temporary state and the fake listener were removed afterward.
- The manual compatibility implementation is also exercised against isolated loopback fake hosts and temporary credential ledgers by `test/t3-compatibility.test.ts`, including the CLI subprocess, read-only probes, baseline acceptance/repeat, both thread views and combined/legacy pending-request tools. `test/t3-contract.test.ts` covers the new strict settlement sample and optional-tool absence on older hosts.
- No production setup, service clone, host credential, Tailscale route or host setting was used. No installed-host upgrade, real-provider launch, runtime fallback or side-chat creation was performed. Source evidence does not establish provider behavior in a running v0.1.6 installation.
